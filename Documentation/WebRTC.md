# WebRTC implementation and call testing

A WebContent process lazily starts one Rust `WebRTCClient` when it first creates a peer connection. The process-wide `WebRTCAgent` routes IPC replies and events by ID. Active peer connections stay rooted until `close()` or document cleanup. Closing stops capture subscriptions, sender tasks and receiver playback, releases channel roots, and tells Rust to release the peer and its resources. Socket loss rejects outstanding requests and closes affected connections; a new connection can start a new helper. The helper exits on socket EOF, and a reaper thread collects its exit status. The browser process does not start a second, unused helper.

Outgoing audio follows `MediaStreamTrack → optional WebAudio processing → resample to 48 kHz → Opus encode → optional worker transform → Rust RTP/DTLS/ICE`. Replacing a track changes the PCM subscription while preserving the backend sender and SSRC. With a script transform attached, frames only reach the transport after the worker writes them back; worker failure does not bypass encryption. Without a transform, ordinary Opus audio goes directly to the transport.

Incoming audio follows `Rust RTP → optional worker transform → Opus decode → platform playback`. The playback buffer and outgoing main-thread handoff are bounded, as is the transform's unread-frame queue. This is still an interim receive path: playback is not driven by `HTMLMediaElement.srcObject`.

The regression tests live under `Tests/LibWeb/Text/input/WebRTC`, plus `WebAudio/AudioWorklet-rate-and-errors.html`. Rust service tests cover ICE configuration, candidate media-section mapping, rollback type, transceiver reuse, per-peer cleanup without disturbing another connection, and receive-only video negotiation with an H.264-only answer. Run the Rust tests with `cargo test -p ladybird_webrtc --lib --offline`. The service tests and browser loopback tests require local socket access.

After rebasing onto `origin/webaudio-proper` (`89dc19c056`), the full `Ladybird`, `WebContent`, `WebWorker`, `test-web`, and `WebRTCClient-build` build passed, along with 28 browser checks, five Rust service tests, and the audio-ring, worklet-pipe, and shared-buffer serialization unit test suites. The browser checks include a mono tone passed between 32 kHz and 44.1 kHz AudioContexts to verify MediaStream source resampling. To run the browser checks:

```sh
Build/release/bin/test-web --test-path Tests/LibWeb \
    --filter WebRTC/ --filter WebAudio/ --filter WebAssembly-imported-function-metadata \
    --test-concurrency 1 --per-test-timeout 45 --temporary-profile \
    --disable-sandbox --enable-autoplay --force-cpu-painting
```

For a Discord echo check, log in through Ladybird and join a voice channel containing only the test user and the echo bot. The bot in `../echo` responds to `!join` and `!leave` and echoes every participant. Test ordinary audio first, then toggle Krisp repeatedly, mute/unmute, change microphones, leave/rejoin, and repeat for a longer call. Compare transport statistics before and after each transition. Do not treat a successful offer/answer or a nonzero packet counter as proof that the audio was decoded or that Krisp processed it.

A local, sandboxed probe of Discord's public Krisp SDK and its 32 kHz model successfully initialized, enabled processing, and suppressed synthetic noise generated by an AudioWorklet at 48 kHz. Before rebasing, the worker produced one second of output in about 1.4 seconds and `CleanAmbientNoiseFloat` averaged 13.8 ms per 10 ms frame; native execution was not verified in that run.

Before the WebAudio architecture rebase, after rebasing onto master `a1db2e3a29`, temporary entry counters confirmed native Wasm execution after startup. With those counters disabled, `CleanAmbientNoiseFloat` averaged 2.31 ms per 10 ms frame over 600 calls, producing six seconds of audio in approximately six seconds. The full browser/helper build, five Rust service tests and 19 browser checks (RTC, AudioWorklet, Wasm and focus regressions) passed. These synthetic measurements establish sufficient processing throughput on the test machine, but do not establish live speech quality or DAVE key-transition reliability. Public assets and temporary instrumentation are not part of the regression suite.

The former worklet implementation reported elapsed time for 500 quanta, synchronous dispatch cost, and exact-zero input/output counts per node. These diagnostics were removed when adopting the render-pipe implementation from `origin/webaudio-proper`. At 48 kHz, 500 quanta represent about 1.33 seconds of audio. Dispatch cost excludes asynchronous worker processing; zero output may be either an underrun or intentional suppression. The latest live Discord run sounded acceptable with Krisp enabled and showed no focus-handler stack overflows or worklet exceptions. Three early decryption failures stopped increasing after key setup, while subsequent frames decrypted successfully and encryption reported no failures. Worklet pacing remained uneven (roughly 1.0–2.35 seconds per 500 quanta), so this short call does not establish sustained reliability.

Remaining work for reliable Discord/Krisp calls:

- Complete renderer sandbox integration: before the rebase, the three local WebRTC tests terminated WebContent with SIGSYS when sandboxing was enabled. The documented RTC test command still disables it. The public Krisp probe runs with browser sandboxing enabled.
- Verify sustained Krisp speech/noise processing and DAVE session/key transitions after login. Local loopback does not establish compatibility with the live client, bot, or server.
- Validate the new AudioWorklet render-pipe implementation under sustained Discord/Krisp load. Modules now execute in a worklet realm, with audio exchanged through bounded render-thread queues. Processor JavaScript is still pumped on the control thread, so page stalls can interrupt processing. Constructor/process errors are reported through `processorerror`. The live-call and synthetic timing results above describe the previous implementation and must be rechecked.
- Route received PCM through MediaStreamTrack and media-element playback. Until that is done, element volume, pause, mute/deafen and sink selection cannot reliably control the interim direct playback path.
- Add RTP-aware receive buffering, reordering, loss concealment and clock-drift handling. A bounded PCM queue limits backlog; it does not replace a jitter buffer.
- Implement echo cancellation, noise suppression and automatic gain constraints. Hardware-specific analyser/capture multipliers are not substitutes for those controls. Device selection and sample-rate conversion are implemented, but microphone level still depends on the input device and application processing.
- Complete sender parameter application, remote transceiver identity/direction reconciliation, configuration updates, ICE restart/glare edge cases and full transport/candidate inspection. Reattaching after `removeTrack()` also needs backend sender-reuse handling; `replaceTrack()` preserves the sender. Statistics come from the backend, but track-scoped statistics and parts of the standard report surface remain incomplete.
- Complete data-channel buffering/backpressure, typed error events, video capture/send/decode/rendering, codec controls, certificates, DTMF and the native SFrame APIs.
- Add longer-running tests for navigation, helper/worker death, device unplugging and network changes. Worker-side transform disposal and full lifecycle behavior need further coverage.

The echo bot itself has unbounded per-user PCM queues and ignores stream backpressure. Repeated `!join` calls can install additional mixers/listeners on an existing connection. Use a fresh `!leave`/`!join` cycle when testing reconnects, and distinguish bot-side backlog from browser-side delay.
